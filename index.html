1. Come usare questa dispensa

Questa dispensa raccoglie tutto ciò che serve per usare Git e GitHub nei tuoi primi progetti, e resta valida dopo la lezione come materiale di consultazione.

È pensata per chi parte da zero. Non serve saper programmare in Java, ma serve saper aprire un terminale e spostarsi tra le cartelle.

Come è organizzata:

  • Le sezioni 2, 3 e 4 spiegano il perché e i concetti: si leggono una volta.

  • Le sezioni da 5 a 9 sono il percorso pratico, nell'ordine in cui lo si fa a lezione.

  • Le sezioni da 10 a 13 servono quando lavori in squadra o quando qualcosa va storto.

  • Le sezioni da 14 a 16 sono da tenere aperte: cheat sheet, glossario e risorse.

Convenzioni usate nel testo:

  • I comandi sono scritti in blocchi di codice, da copiare nel terminale.

  • Ciò che è tra parentesi angolari, come <nome>, va sostituito con il tuo valore, senza le parentesi.

  • «Terminale» indica Terminal su macOS e Linux, oppure Git Bash o PowerShell su Windows.

Cosa ti serve per seguire la lezione: un computer con Git installato (sezione 5), un account GitHub gratuito e un editor di testo o un IDE come IntelliJ IDEA, Eclipse o VS Code.

2. Perché il controllo di versione

Un sistema di controllo di versione registra i cambiamenti a un insieme di file nel tempo e permette di richiamare una versione precisa in qualsiasi momento. Si usa soprattutto per il software, ma funziona con qualsiasi file di testo.

Senza, si finisce a lavorare così:

progetto.zip
progetto_v2.zip
progetto_v2_DEFINITIVO.zip
progetto_v2_DEFINITIVO_ok_davvero.zip

Questo metodo lascia tre domande senza risposta:

  • Chi ha cambiato cosa, e quando?

  • Come si torna alla versione di martedì scorso?

  • Come lavorano in tre sullo stesso file senza sovrascriversi?

Git risponde a tutte e tre. Ogni modifica salvata ha un autore, una data e un messaggio che ne spiega il motivo. Ogni versione passata resta recuperabile. E più persone possono lavorare sullo stesso progetto in parallelo, unendo poi il lavoro.

Git è nato nel 2005, creato da Linus Torvalds e dagli sviluppatori del kernel Linux per gestire un progetto enorme con centinaia di collaboratori. Oggi è lo standard del settore: quasi ogni azienda che sviluppa software lo usa.

Cosa significa «distribuito»

Git è un sistema di controllo di versione distribuito. Ogni copia del progetto sul tuo computer contiene l'intera storia, non solo i file attuali. Per questo quasi tutte le operazioni sono locali, quindi veloci, e si può lavorare anche senza connessione.

Git registra fotografie, non differenze

Ogni volta che salvi lo stato del progetto, Git ne fa una fotografia (in gergo snapshot). Se un file non è cambiato rispetto alla fotografia precedente, Git non lo copia di nuovo: tiene un collegamento a quello vecchio.

Git inoltre usa dei codici di controllo (checksum) per riconoscere ogni modifica. Per questo è praticamente impossibile cambiare un file senza che Git se ne accorga. Di norma si aggiungono solo dati: anche una cancellazione è una nuova informazione registrata, quindi si può annullare.

3. Git e GitHub: due cose diverse

Git è lo strumento che gestisce le versioni; GitHub è un sito che ospita repository Git. Si può usare Git senza GitHub, ma non si può usare GitHub senza Git.

GitGitHub
Cos'èProgramma di controllo di versioneServizio web che ospita repository Git
Dove viveSul tuo computerSu internet
CostoGratuito e open sourceAccount gratuito, piani a pagamento per funzioni avanzate
Come si usaDal terminale o da un IDEDal sito web, insieme a Git
Cosa dà in piùStoria, branch, mergePull request, issue, review, profilo pubblico

Esistono piattaforme equivalenti a GitHub, come GitLab e Bitbucket. Funzionano tutte con Git: quello che impari qui vale anche per loro.

Cosa aggiunge GitHub a Git

  • Backup nel cloud. Il codice vive anche fuori dal tuo computer.

  • Lavoro di squadra. Le pull request e le review servono a decidere insieme cosa entra nel progetto.

  • Issue. Segnalazioni e attività da fare, collegabili al codice.

  • Open source. Moltissimi progetti pubblici da leggere, copiare e migliorare.

  • Vetrina. Il tuo profilo mostra cosa sai fare a chi seleziona sviluppatori.

  • Automazioni. Con GitHub Actions si possono lanciare test e controlli a ogni modifica.

Tre modi di usare Git

Gli stessi repository si possono gestire in modi diversi, e puoi alternarli:

  • Terminale. Il modo più completo e quello che trovi in azienda. È quello che usiamo a lezione.

  • Interfaccia grafica. GitHub Desktop è la più semplice per iniziare; anche gli IDE hanno un pannello Git integrato.

  • GitHub CLI. Il comando gh permette di fare dal terminale cose che altrimenti si fanno sul sito, come accedere o aprire una pull request.

Imparare i comandi serve anche se userai un'interfaccia grafica: i nomi delle operazioni sono gli stessi, e quando qualcosa va storto i messaggi parlano il linguaggio dei comandi.

4. Concetti chiave

Prima dei comandi servono poche parole. Se le hai chiare, i comandi diventano ovvi.

TermineSignificato
Repository (repo)La cartella di un progetto insieme a tutta la sua storia. Sul disco la storia sta nella cartella nascosta .git.
CommitUna fotografia del progetto in un momento preciso, con autore, data e messaggio.
Working directoryI file così come li vedi e li modifichi sul disco.
Staging areaUna sala d'attesa: qui scegli quali modifiche entreranno nel prossimo commit.
BranchUna linea di sviluppo parallela. Permette di provare una modifica senza toccare il codice stabile.
mainIl branch principale, quello che deve sempre funzionare.
RemoteUna copia del repository ospitata altrove, di solito su GitHub.
originIl nome che Git dà di solito al remote da cui hai clonato o che hai collegato.
CloneLa copia completa di un repository remoto sul tuo computer, storia compresa.
ForkLa tua copia personale, su GitHub, del repository di qualcun altro.
Pull request (PR)La richiesta di far entrare le tue modifiche in un altro branch o repository.
MergeL'unione di due linee di sviluppo.

Le tre aree in cui vivono i file

Ogni modifica passa per tre aree locali prima di arrivare su GitHub:

  1. Working directory. Modifichi i file con il tuo editor.

  2. Staging area. Con git add indichi cosa vuoi salvare.

  3. Repository locale. Con git commit la modifica entra nella storia.

Solo dopo git push il commit arriva su GitHub. Questo percorso è il filo conduttore di tutta la dispensa.

Perché esiste lo staging

Puoi aver cambiato cinque file ma voler salvare solo due, perché riguardano la stessa correzione. Lo staging ti lascia scegliere. Il risultato è una storia pulita, dove ogni commit racconta una cosa sola.

Locale e remoto

Il repository sul tuo computer e quello su GitHub sono due copie separate. Non si aggiornano da sole: sei tu a inviare le novità con git push e a scaricarle con git pull. Se capisci questo, hai capito metà di Git.

5. Installazione e configurazione

Per lavorare servono tre cose: Git sul computer, un account GitHub e un modo per autenticarti. Fai le installazioni una volta sola.

Git sul tuo computer in tre passi

Non dare per scontato che Git sia già installato: sul computer di casa di solito non c'è. Segui sempre questi tre passi, nell'ordine.

Passo 1. Controlla se Git esiste. Apri il terminale (Terminale su macOS e Linux, PowerShell su Windows) e scrivi:

git version

  • Se compare una riga come git version 2.47.0, Git c'è già: salta al passo 3 e poi alla configurazione.

  • Se compare un errore come git: command not found o 'git' is not recognized, Git non è installato: vai al passo 2.

Passo 2. Installa Git, se manca. Scegli il tuo sistema.

Windows. Il modo più rapido è da PowerShell:

winget install --id Git.Git -e

Se winget non funziona, scarica l'installer da git-scm.com, avvialo e accetta le opzioni predefinite cliccando sempre Next. L'installazione aggiunge anche Git Bash, un terminale che capisce i comandi di questa dispensa.

macOS. Scrivere git version fa spesso comparire una finestra che propone di installare gli strumenti da riga di comando: clicca Installa e attendi la fine. Se la finestra non compare, lancia:

xcode-select --install

Se usi Homebrew, puoi invece installare con brew install git.

Linux (Debian e Ubuntu).

sudo apt update
sudo apt install git

Passo 3. Conferma che sia tutto a posto. Chiudi il terminale e riaprilo: senza questo passaggio il sistema non vede il programma appena installato. Poi ripeti il controllo:

git version

Se compare il numero di versione, Git è pronto. Se compare ancora l'errore, riavvia il computer e riprova; se non cambia nulla, chiedi aiuto al docente prima di andare avanti.

Dire a Git chi sei

Ogni commit riporta nome ed email dell'autore. Configurali una volta sola:

git config --global user.name "Nome Cognome"
git config --global user.email "tua-email@esempio.it"
git config --global init.defaultBranch main

Usa la stessa email del tuo account GitHub, così i commit risultano collegati al tuo profilo. Per controllare la configurazione scrivi git config --global --list.

Creare l'account GitHub

  1. Vai su github.com e scegli Sign up.

  2. Inserisci email, password e uno username.

  3. Conferma l'email con il codice che ricevi.

Lo username finisce nell'indirizzo del tuo profilo, e potrebbe finire in un curriculum. Scegline uno semplice e professionale, per esempio nome e cognome.

Autenticarsi

GitHub non accetta più la password dell'account quando lavori da terminale su HTTPS. Serve un altro tipo di accesso, e dipende dal sistema.

Windows. Non devi installare nulla: Git for Windows include Git Credential Manager. Al primo git push si apre una finestra del browser: accedi a GitHub e conferma. Da quel momento Git ricorda l'accesso.

macOS. Git non apre il browser. Usa un token personale, che al primo push incolli al posto della password:

  1. Su github.com clicca la tua foto in alto a destra, poi Settings.

  2. In fondo al menu a sinistra scegli Developer settings, poi Personal access tokens, poi Tokens (classic).

  3. Clicca Generate new token (classic). Dai un nome, scegli una scadenza (30 giorni vanno bene) e spunta la casella repo.

  4. Clicca Generate token e copia subito il token: GitHub lo mostra una volta sola.

  5. Al primo git push Git chiede lo username (il tuo username GitHub) e la password: incolla il token. Il portachiavi di macOS lo salva e non te lo chiede più.

Linux. Come su macOS: token personale al posto della password.

Alternativa per tutti: GitHub CLI. Dopo averlo installato (pacchetto da cli.github.com; su Mac anche brew install gh), il comando gh auth login guida l'accesso dal browser e configura Git al posto tuo. Non è incluso con Git: senza installazione il terminale risponde command not found.

Un token funziona come una password: non scriverlo mai nel codice, non metterlo in un repository e non condividerlo.

Se qualcosa non va

  • git: command not found: Git non è installato o il terminale va riaperto.

  • Il push chiede una password e la rifiuta: stai usando la password dell'account. Usa una delle tre strade qui sopra.

  • I commit non compaiono sul profilo: l'email configurata non coincide con quella dell'account GitHub.

6. Il ciclo di lavoro quotidiano

Quasi tutto il lavoro con Git è la ripetizione di quattro gesti: guarda, aggiungi, salva, invia. Imparali a memoria.

Creare un repository locale

Entra nella cartella del progetto e lancia:

cd mio-progetto
git init

Git crea la cartella nascosta .git. Da questo momento la cartella è un repository, ma la sua storia è ancora vuota.

Vedere cosa è cambiato

git status

È il comando che userai di più. Ti dice quali file sono nuovi, quali modificati e quali già pronti per il commit. Nel dubbio, lancia git status.

Scegliere cosa salvare

git add Main.java
git add .

Il primo comando mette in staging un file; il secondo tutti i file modificati nella cartella corrente. Prima di usare il punto, controlla con git status che non ci siano file che non vuoi.

Salvare la fotografia

git commit -m "Aggiunge la classe Main con il saluto"

Il messaggio dice cosa hai cambiato e, se serve, perché. Tra qualche mese sarà l'unica spiegazione che avrai.

Rivedere la storia

git log
git log --oneline

Il primo mostra ogni commit con autore e data; il secondo una riga per commit. Se la lista è lunga, esci con il tasto q.

Vedere le differenze

git diff
git diff --staged

Il primo confronta il working directory con lo staging; il secondo confronta lo staging con l'ultimo commit. Anche qui, q per uscire.

Escludere file con .gitignore

Alcuni file non vanno nel repository: file compilati, impostazioni dell'IDE, password. Si elencano in un file chiamato .gitignore, nella cartella principale:

target/
.idea/
*.class
.env

Crealo prima del primo commit. Un file già committato non viene ignorato retroattivamente: va tolto con git rm --cached nome-file.

Il ciclo completo

PassoComandoCosa succede
1. Modifichi(il tuo editor)Cambiano i file nel working directory
2. Guardigit statusVedi lo stato di ogni file
3. Aggiungigit addLe modifiche vanno in staging
4. Salvigit commit -m "..."Nasce un commit nel repository locale
5. Inviigit pushIl commit arriva su GitHub

7. Lavorare con GitHub

Hai due modi per collegare una cartella a GitHub: partire da una cartella tua e collegarla a un repository nuovo, oppure clonare un repository che esiste già. Il risultato è lo stesso.

Percorso A: dalla cartella locale a GitHub

  1. Su github.com scegli New repository, dai un nome e lascia il repository vuoto: niente README, niente .gitignore.

  2. Copia l'indirizzo che GitHub ti mostra, simile a https://github.com/tuo-username/mio-progetto.git.

  3. Nella cartella locale, dopo almeno un commit, collega il remoto e invia:

git remote add origin https://github.com/tuo-username/mio-progetto.git
git branch -M main
git push -u origin main

Il -u ricorda il collegamento: dopo la prima volta basta scrivere git push. Per controllare i remoti collegati usa git remote -v.

Percorso B: clonare un repository esistente

git clone https://github.com/utente/repository.git
cd repository

Il clone scarica tutto: file, storia e collegamento a origin. Non serve né git init né git remote add. Un repository pubblico si può clonare senza account; per fare push servono permessi di scrittura.

Inviare le modifiche: push

git push

I commit che hai solo in locale arrivano su GitHub. Ricarica la pagina del repository per vederli.

Scaricare le novità: pull

git pull

Scarica i commit che altri hanno inviato e li unisce al tuo lavoro. Fallo sempre prima di iniziare a lavorare e prima di un push.

Quando il push viene rifiutato

Se vedi rejected e fetch first, qualcuno ha inviato commit che tu non hai. Git non ti lascia sovrascriverli. La soluzione è sempre la stessa:

git pull
git push

Se il pull segnala un conflitto, vai alla sezione sui branch e sul merge.

HTTPS o SSH

L'indirizzo del repository può avere due forme: https://github.com/... oppure git@github.com:.... La prima usa l'accesso web visto nella sezione 5, la seconda le chiavi SSH. I comandi non cambiano. Se hai sbagliato forma, correggi con git remote set-url origin <nuovo-indirizzo>.

Schema riassuntivo

Voglio...Comando
Copiare un repo da GitHubgit clone <url>
Collegare una cartella mia a un repo vuotogit remote add origin <url>
Inviare i miei commitgit push
Scaricare i commit degli altrigit pull
Vedere a quale remoto sono collegatogit remote -v

8. Branch e merge

Un branch è una linea di sviluppo separata. Ti permette di lavorare a una funzione nuova senza rischiare di rompere main, e permette a più persone di lavorare in parallelo.

Perché usarli

Immagina che tu e un collega modifichiate lo stesso progetto. Se lavorate entrambi su main, vi pestate i piedi a ogni push. Se ognuno ha il suo branch, le modifiche si uniscono solo quando sono pronte.

Comandi essenziali

git branch
git switch -c nome-branch
git switch main
git branch -d nome-branch

  • git branch elenca i branch locali; quello attuale ha un asterisco.

  • git switch -c crea un branch nuovo e ci passa sopra.

  • git switch torna su un branch esistente.

  • git branch -d elimina un branch già unito.

I file nella cartella cambiano quando cambi branch: è normale, Git mostra la versione di quel ramo. Se hai modifiche non salvate, Git può rifiutarsi di cambiare. Fai prima un commit.

Dare un buon nome ai branch

Un nome breve che dice cosa fai: fix-login, aggiungi-readme, esercizio-2. Evita spazi e maiuscole.

Unire un branch: merge

Per portare il lavoro di un branch dentro main:

git switch main
git pull
git merge nome-branch

Sei tu a decidere dove arrivano le modifiche: ti sposti sul branch di destinazione e unisci quello di origine. Su GitHub questo passaggio si fa di solito con una pull request (sezione 9).

Inviare un branch a GitHub

git push -u origin nome-branch

La prima volta serve -u. Poi basta git push.

I conflitti

Un conflitto nasce quando due persone modificano le stesse righe dello stesso file. Git non può scegliere al posto tuo, quindi si ferma e ti chiede aiuto. Non è un errore grave, è una domanda.

Git segna il file in questo modo:

<<<<<<< HEAD
System.out.println("Ciao");
=======
System.out.println("Buongiorno");
>>>>>>> nome-branch

La parte tra <<<<<<< e ======= è la tua versione; quella tra ======= e >>>>>>> è l'altra.

Risolvere un conflitto, passo per passo

  1. Lancia git status: i file in conflitto compaiono come both modified.

  2. Apri il file e decidi cosa tenere: una versione, l'altra o una combinazione.

  3. Cancella le tre righe con <<<<<<<, ======= e >>>>>>>. Devono sparire tutte.

  4. Salva il file, poi git add nome-file.

  5. Concludi con git commit e, se serve, git push.

Se ti spaventi, puoi tornare allo stato precedente con git merge --abort. Il consiglio per evitare i conflitti è semplice: fai git pull spesso e lavora su file diversi quando possibile.

9. Fork e pull request

Non puoi fare push nel repository di uno sconosciuto, e non vorresti che lo facesse nessuno nel tuo. Fork e pull request sono il modo in cui GitHub risolve il problema.

Il flusso in sintesi

  1. Fork. Crei la tua copia del repository sul tuo account GitHub.

  2. Clone. Scarichi il tuo fork sul computer.

  3. Branch e commit. Lavori su un branch e salvi le modifiche.

  4. Push. Invii il branch al tuo fork.

  5. Pull request. Chiedi al proprietario del repository originale di accogliere le tue modifiche.

  6. Review e merge. Il proprietario guarda, commenta e, se va bene, unisce.

Fork

In alto a destra, nella pagina del repository, c'è il pulsante Fork. Scegli il tuo account e GitHub crea la copia. Il fork resta collegato all'originale, che si chiama upstream, ma i due si aggiornano separatamente.

La pull request

Dopo il push del tuo branch, GitHub mostra un pulsante per aprire una pull request. Scrivi un titolo chiaro e una breve descrizione: cosa hai cambiato e perché. La PR mostra tutte le differenze nella scheda Files changed.

Chi riceve la PR può commentare le righe, chiedere correzioni, approvare. Se aggiungi altri commit allo stesso branch e fai push, la PR si aggiorna da sola.

Come si chiude una PR

Quando la PR è approvata, il maintainer sceglie come unirla:

  • Create a merge commit. Mantiene tutti i commit e aggiunge un commit di unione.

  • Squash and merge. Raggruppa tutti i commit in uno.

  • Rebase and merge. Riapplica i commit uno per uno, senza commit di unione.

Non devi scegliere tu, quando contribuisci a un progetto altrui. Una PR può anche essere chiusa senza unione, ed è un esito normale.

Pull request anche dentro lo stesso repository

In squadra di solito non si usa il fork: ognuno ha i permessi sul repository comune, crea un branch e apre una PR verso main. Il flusso è identico, salvo i primi due passi.

Un caso reale: diskuse

Il repository msciab/diskuse di Michele Sciabarra è pubblico. Nell'esercizio lo cloniamo e guardiamo la sua storia. Sulla pagina del repository trovi:

  • il pulsante Code, da cui copi l'indirizzo per il clone;

  • la scheda Pull requests, dove si vede come altri hanno proposto modifiche;

  • la scheda Commits, con l'intera storia del progetto.

Leggere repository di altri è il modo più veloce per imparare come lavorano i professionisti.

Contribuire a un progetto open source

Prima di aprire una PR su un progetto altrui, leggi il file README e, se c'è, CONTRIBUTING.md. Spesso spiegano le regole di stile e il processo. Per cominciare, cerca le issue con l'etichetta good first issue.

10. Annullare e recuperare

Git è una rete di sicurezza: quasi tutto quello che hai salvato in un commit si può recuperare. Il comando giusto dipende da dove si trova l'errore.

SituazioneComando
Ho modificato un file e voglio buttare le modifichegit restore file
Ho fatto git add per sbagliogit restore --staged file
Ho sbagliato il messaggio dell'ultimo commit (non ancora inviato)git commit --amend -m "nuovo messaggio"
Voglio annullare un commit già inviatogit revert <commit>
Voglio tornare indietro in locale, buttando commitgit reset --hard <commit>
Ho perso dei commitgit reflog

Buttare le modifiche non salvate

git restore Main.java

Il file torna com'era nell'ultimo commit. Attenzione: le modifiche buttate non si recuperano, perché non erano mai state salvate.

Togliere un file dallo staging

git restore --staged Main.java

Il file resta modificato sul disco, ma non entrerà nel prossimo commit.

Correggere l'ultimo commit

git commit --amend -m "Messaggio corretto"

Va bene solo se il commit non è ancora stato inviato con push. Cambiare la storia già condivisa crea problemi a chi lavora con te.

Annullare un commit già condiviso: revert

git log --oneline
git revert a1b2c3d

Il codice a1b2c3d è l'inizio dell'identificativo del commit, visibile in git log --oneline. Il comando crea un nuovo commit che fa l'operazione inversa. La storia resta intatta ed è la scelta sicura quando il lavoro è già su GitHub.

Tornare indietro: reset

git reset --hard a1b2c3d

Sposta il branch su quel commit e butta tutto quello che c'era dopo, comprese le modifiche non salvate. È un comando distruttivo: usalo solo sul tuo lavoro locale, mai su commit già inviati a GitHub.

Il paracadute: reflog

git reflog

Elenca tutti i punti in cui è stato il tuo repository, anche quelli che git log non mostra più. Se un reset ti ha fatto perdere dei commit, trova qui il loro codice e torna indietro con git reset --hard <codice>.

Regola pratica: finché una cosa è stata committata, è quasi sempre recuperabile. Quello che non è mai stato committato, no.

11. Git nei progetti Java

Un progetto Java produce molti file che non sono codice tuo: classi compilate, impostazioni dell'IDE, cartelle di build. Vanno esclusi dal repository, altrimenti ogni commit si riempie di rumore.

Cosa va nel repository

  • Il codice sorgente (src/).

  • I file di build (pom.xml per Maven, build.gradle per Gradle).

  • Il README.md e il .gitignore.

Cosa non ci va

  • Le classi compilate (*.class) e le cartelle di build (target/, build/).

  • Le impostazioni personali dell'IDE (.idea/, *.iml, .vscode/).

  • I file con credenziali (.env, application-local.properties).

  • I file di sistema (.DS_Store, Thumbs.db).

Un .gitignore di partenza

# Build
target/
build/
*.class
*.jar

# IDE
.idea/
*.iml
.vscode/
.project
.classpath
.settings/

# Sistema
.DS_Store
Thumbs.db

# Segreti e configurazioni locali
.env
application-local.properties

Puoi anche partire da un modello: nella creazione del repository su GitHub, il menu Add .gitignore offre il modello Java.

Git dentro l'IDE

IntelliJ IDEA, Eclipse e VS Code hanno un pannello Git integrato. Mostra i file modificati, permette di fare commit e push con un clic e visualizza le differenze riga per riga.

Le operazioni sono quelle che hai imparato: cambiano solo i pulsanti. Se l'IDE ti dà un errore che non capisci, apri il terminale nella cartella del progetto e lancia git status.

Aprire un progetto clonato

  1. Clona il repository con git clone.

  2. Nell'IDE scegli Open e seleziona la cartella clonata.

  3. Lascia che l'IDE importi la configurazione Maven o Gradle.

Attenzione ai file già tracciati

Se hai fatto un commit prima di creare il .gitignore, i file indesiderati ci sono già. Rimuovili dal controllo di versione, senza cancellarli dal disco:

git rm -r --cached .idea target
git commit -m "Rimuove file di build e IDE dal repository"

12. Buone pratiche

Git permette quasi tutto. Le buone pratiche sono le abitudini che rendono il lavoro leggibile per chi verrà dopo di te, compreso te stesso tra sei mesi.

Cinque regole per non pentirsi

  1. Commit piccoli, con un messaggio chiaro. Una modifica logica per commit.

  2. Prima di iniziare git pull, prima di chiudere git push. Così lavori sempre sull'ultima versione.

  3. Non lavorare direttamente su main. Crea un branch per ogni attività.

  4. Mai password, token o chiavi nel repository. Usa il .gitignore.

  5. Nel dubbio, git status. Ti dice dove sei e cosa è successo.

Come scrivere un buon messaggio di commit

Il messaggio risponde alla domanda: cosa fa questo commit? Una riga breve, al presente, che descrive il risultato.

Da evitareMeglio
modificheAggiunge la validazione dell'email nel form
fixCorregge il calcolo del totale con sconto
ultimo commit prima di cenaRinomina la classe Cliente in Customer

Se serve spiegare il perché, scrivi una riga vuota e poi un paragrafo di dettaglio. Puoi usare git commit senza -m per aprire l'editor.

Regole di squadra

Quando si lavora in gruppo sullo stesso repository, conviene mettersi d'accordo all'inizio:

  • Chi unisce in main. Per esempio solo dopo l'approvazione di un compagno.

  • Come si chiamano i branch. Per esempio feature/nome e fix/nome.

  • Chi lavora su cosa. Due persone sullo stesso file significano conflitti quasi certi.

  • Ogni quanto si fa pull. Almeno all'inizio di ogni sessione di lavoro.

  • Lingua dei messaggi. Italiano o inglese, ma sempre la stessa.

Il README

Ogni repository dovrebbe avere un README.md che spiega cos'è il progetto, come si avvia e come si usa. È la prima cosa che vede chi apre il tuo repository, e conta molto in un portfolio. Si scrive in Markdown, un linguaggio semplice per formattare il testo.

I segreti

Password, token di accesso, chiavi di servizi esterni e credenziali del database non vanno mai nel repository, nemmeno in un repository privato.

Git conserva tutta la storia: cancellare il file in un commit successivo non basta, perché il segreto resta nei commit precedenti. Se un segreto è finito su GitHub, consideralo compromesso: cambialo subito e solo dopo pensa a ripulire il repository.

Cosa non fare

  • Non usare git push --force su rami condivisi: può cancellare il lavoro degli altri.

  • Non committare file enormi o binari inutili.

  • Non fare un solo commit gigante a fine giornata.

  • Non rimandare i pull: più aspetti, più grandi saranno i conflitti.

13. Problemi comuni e soluzioni

Quando Git dà un errore, leggi il messaggio per intero: di solito dice anche cosa fare. Questa tabella raccoglie i casi che incontrerai più spesso.

Messaggio o sintomoCausaSoluzione
git: command not foundGit non è installato, o il terminale è stato aperto prima dell'installazioneInstalla Git; chiudi e riapri il terminale
fatal: not a git repositorySei in una cartella che non è un repositoryEntra nella cartella giusta con cd, oppure lancia git init
Author identity unknownNome ed email non configuratigit config --global user.name e user.email (sezione 5)

Un metodo per ogni problema

  1. Leggi il messaggio. Spesso contiene la soluzione.

  2. Lancia git status. Ti dice in che stato è il repository.

  3. Non improvvisare comandi distruttivi. reset --hard e push --force si usano solo quando sai cosa fai.

  4. Copia il messaggio d'errore e cercalo. È quello che fanno tutti gli sviluppatori.

  5. Chiedi aiuto con il contesto giusto. Porta l'output di git status e git log --oneline.

Mettere da parte il lavoro: stash

Se devi cambiare branch ma non sei pronto a fare un commit:

git stash
git switch altro-branch
...
git switch branch-originale
git stash pop

git stash mette le modifiche in un cassetto temporaneo; git stash pop le riprende.

Ultima risorsa

Se il repository locale è in uno stato che non capisci, e il lavoro importante è già su GitHub, puoi sempre clonare di nuovo in una cartella nuova. Non è elegante, ma funziona.

16. Per approfondire

  • Pro Git di Scott Chacon e Ben Straub: il libro ufficiale, gratuito e disponibile anche in italiano su git-scm.com/book.

  • Documentazione di GitHub su docs.github.com, con guide per ogni funzione.

  • GitHub Skills su skills.github.com: piccoli corsi interattivi che si svolgono dentro un repository vero.

  • Learn Git Branching su learngitbranching.js.org: un gioco visuale per capire branch e merge.

  • Oh Shit, Git!?! su ohshitgit.com: soluzioni rapide ai problemi più comuni, in inglese.

  • Il git help: scrivendo git help commit (o qualsiasi altro comando) si apre il manuale integrato.

Come continuare dopo il corso

  1. Crea un repository per ogni esercizio di Java che svolgi.

  2. Scrivi un README per ognuno, anche breve.

  3. Contribuisci a un piccolo progetto open source, anche solo correggendo un refuso nella documentazione.

  4. Usa branch e pull request anche nei progetti personali: è l'allenamento migliore.
